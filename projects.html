Telegram Task Manager Agent

n8nAI AgentTelegramGoogle SheetsStructured Output
Built +
Problem

A task bot that saves to a spreadsheet is only useful if it never makes things up. The usual failure is the model filling in a due date or a priority the user never said. Once one wrong row is saved, you stop trusting the whole list.

Solution

A Telegram bot that manages a task list in Google Sheets, with one rule: it is not allowed to guess. A task is only saved once the date, description, category and priority are all there. If anything is missing, it asks a question instead of picking a default. The same bot also sends a short list of today's tasks every morning, grouped by priority.

How it works

Both the chat and the morning message go through the same agent. Only the instructions change depending on which one triggered it, so I keep one set of tools instead of building two separate workflows.

Today's date, tomorrow's date and the current time are passed in directly, set to Amman time. This is the part that usually breaks these bots, because "tomorrow" means nothing to a model that doesn't know today. A small script works out the next task ID from the rows already in the sheet, rather than asking the model to count. Another script cleans up the agent's reply before it goes back to Telegram, since an LLM can return plain text, JSON as text, or an object, and all three need to end up as one message. Models run on OpenRouter, with Groq set as a backup if the first one fails.

Gym Membership Voice Assistant

n8nSpeech-to-TextText-to-SpeechElevenLabsAI Agent
Built +
Problem

Front desk questions at a gym repeat all day: what plans are there, what do they cost, sign me up, cancel my membership. And people send voice notes as often as they type.

Solution

A Telegram assistant that answers membership questions by voice or text, and replies the same way you asked. It can look up a member, give current prices, add a new member, and cancel one, all against a live spreadsheet. That way the answers come from real records, not from something written into the prompt months ago.

How it works

Incoming messages are sorted by type. Voice notes are downloaded and turned into text by ElevenLabs; typed messages skip that step. Both then reach the same agent.

The agent gets four specific tools: read a member, read prices, add a member, cancel a member. It does not get open access to the spreadsheet. Keeping the tools narrow means everything it can do is written down and nothing else is possible. On the way out, the reply is turned back into speech if the question came in as a voice note.

Same Bot, Three Designs — a Comparison

n8nAgent DesignStructured OutputTool Calling
Built +
Problem

"An agent that writes to a database" can be built in several ways, and they only look different when something goes wrong. I wanted to see them next to each other instead of guessing.

Solution

The same small assistant, give one piece of advice and save it, built three ways on one screen. First: the agent's plain text gets saved by the next step. Second: the same thing, but the reply must match a fixed format first. Third: the agent is given the spreadsheet as a tool and saves the row itself.

What I learned

Forcing the reply into a fixed format before it gets saved is what stops broken rows. Handing the agent the save tool gives it more freedom and more ways to get it wrong. That result is why the task manager above is built the way it is.

LLM & RAG

Self-Updating RAG Knowledge Base

RAGPineconeEmbeddingsGoogle Driven8n
Built +
Problem

A RAG system that needs someone to press a button goes out of date the moment a new file is added to the folder. The easy fix is to reload everything on a timer, but then you pay to process the same documents over and over and end up with duplicates.

Solution

A knowledge base that keeps itself up to date. It checks a Google Drive folder on a schedule, loads only the files it hasn't seen before, and answers questions using only what has been loaded.

How it works

On each run it lists the Drive folder and compares it against a record of files already processed in Google Sheets. A small script works out which files are new, and only those go through the loop that downloads, splits and processes them. Documents are cut into chunks, turned into vectors using HuggingFace, and stored in Pinecone.

On the question side, the search is given to the agent as a tool instead of being pushed into every prompt. So the agent decides when it actually needs to look something up. Models run on OpenRouter with Groq as a backup.

Teaching a Model to Say "I Don't Know"

Bayesian Neural NetworksMulti-LabelUncertainty
Write-up +
Read it on GitHub ↗
Problem

A normal classifier always picks something. Its scores are forced to add up to 100%, so an image of a cat shown to a model trained on dogs and horses still comes back confidently labelled as one of them. There is no option to say "this is none of them".

Solution

Two ways around it, worked through in the repository. One is a Bayesian neural network, which carries how unsure it is as part of the answer. The other is scoring every class on its own instead of making them compete, so all the scores can come back low at once and the model can reject the input.

How it works

The repository has the full explanation plus a notebook with the second approach implemented. It's a written study rather than an app, so it's linked instead of shown in screenshots.

WhatsApp Messaging Platform at Scale

WhatsApp Cloud APIMongoDBWebhook SecuritySelf-hosted n8nHostinger VPS
Production +

Client work. I describe the engineering only. No diagrams, no workflow files, no client details.

Problem

Sending WhatsApp messages at scale on the official API means living with its rules. Message templates need approval before you can use them. There are limits on how fast you can send. Delivery updates arrive out of order. And any image you upload stops working after 30 days, which quietly breaks every message that points at it.

Solution

A set of workflows sitting between a web app and the WhatsApp Business Cloud API. They handle sending, incoming replies, scheduled reminders, and the background jobs that stop the whole thing falling apart over time. MongoDB holds the truth about what was sent, what was delivered, and who replied.

How it works

Messages go out as approved templates. Replies come back on webhooks and get matched to the right record in MongoDB.

Every webhook is checked before it is trusted. There is a shared secret passed between the app and the workflows, and a signature check on the callbacks coming from Meta. These endpoints have to be publicly reachable to work at all, so the check is what stops anyone else from driving them.

Large sends are broken into batches with pauses between them instead of being fired all at once, which is what keeps them inside the rate limits. Scheduled jobs cover anything based on time: reminders for people who haven't replied, follow-ups, and expiry. The 30-day image problem is handled by a job that re-uploads the files and updates the stored references before they run out. A cleanup job removes files nobody points at any more, so the server disk doesn't slowly fill up.

Also part of this

Running and looking after n8n myself on a Hostinger VPS: setting it up, managing credentials, HTTPS, making sure nothing is lost on restart, and keeping scheduled workflows alive.

Problem

Finding and naming Jordanian money in a photo. Notes and coins together, in normal room lighting, at whatever angle the picture was taken. No public dataset for this existed.

Solution

A model that finds every note and coin in a photo, marks each one with its value, and counts them up. It runs as a web app where you upload a picture and get the marked-up result back.

Fire Detection from Sensor Readings

Scikit-learnNeural NetworkEnsemblesStreamlit
Live demo +
Try it now ↗ GitHub ↗
Problem

Spotting a fire from sensor readings early enough to be worth something. One model gives you a yes or a no and no sense of how sure it is, which for a safety warning is exactly what you want to know.

Solution

A web app that takes thirteen sensor readings — temperature, humidity, gas and air quality levels, pressure, and particle counts — and shows what seven different models each think. When all seven agree, that means far more than any one of them saying so alone.

How it works

Seven models trained on a public smoke detection dataset: logistic regression, decision tree, random forest, naive Bayes, gradient boosting, a voting ensemble that combines several of them, and a neural network built in Keras. All seven are saved and loaded by the app, which runs every one on your input and shows the answers side by side instead of hiding any disagreement behind a single number. Deployed on Streamlit.
