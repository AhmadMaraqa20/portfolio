AI Agents & Assistants

Telegram Task Manager Agent

n8nAI AgentTelegramGoogle SheetsStructured Output
Working +
Problem

A task assistant that writes to a spreadsheet is only useful if it never invents data. The obvious failure mode is the model helpfully filling in a due date or a priority the user never gave — and once a wrong row is written, the whole list stops being trustworthy.

Solution

A Telegram agent that manages a task list in Google Sheets under a strict zero-default policy: it is forbidden from guessing. A task is only written once the date, description, category, and priority are all present; anything missing turns into a follow-up question instead of a default value. A second entry point runs on a schedule and sends a morning briefing of the day's tasks, grouped by priority.

Implementation

One agent serves both paths — a Telegram trigger and a schedule trigger — with the system prompt swapped per mode, so the conversational assistant and the daily briefing share the same tools instead of being two separate workflows. Current date, tomorrow, and time are injected as explicit anchors in the Asia/Amman timezone, because relative dates like "tomorrow" are where these agents break most often. A code node computes the next task ID from the existing rows rather than trusting the model to count, and a validation node normalizes the agent's output before it reaches Telegram — handling the cases where an LLM returns a raw string, stringified JSON, or an object under a different key. Models run through OpenRouter with Groq as fallback.

Gym Membership Voice Assistant

n8nSpeech-to-TextText-to-SpeechElevenLabsAI Agent
Working +
Problem

Front-desk questions at a gym are repetitive — what plans exist, what they cost, signing someone up, cancelling a membership — and they arrive as voice notes as often as text.

Solution

A Telegram assistant that handles membership enquiries in either voice or text and answers in the same format the user used. It can look up an existing member, quote current prices, register a new member, and deactivate one — all against a live spreadsheet, so the answers reflect real records rather than anything memorized in the prompt.

Implementation

A switch node routes incoming Telegram messages by type: voice notes are downloaded and transcribed through ElevenLabs, text passes straight through, and both converge on the same agent. The agent is given four scoped tools — read member, read prices, add member, deactivate member — rather than open database access, which keeps what it can do explicit. On the way out, a second switch mirrors the input format: voice in means the reply is synthesized back to speech and sent as an audio file.

Daily Coach — Three Architectures Compared

n8nAgent DesignStructured OutputTool Calling
Study +
Problem

"Agent writes to a database" can be built several ways, and the differences only show up under failure. I wanted to see them next to each other rather than argue about them in the abstract.

Solution

The same assistant — give advice, log it — built three ways in one canvas: the agent's raw text appended by a following node; the agent forced through a structured output parser before writing; and the agent given the sheet as a tool it calls itself.

Implementation

Three parallel branches sharing the same trigger and model setup so only the architecture varies. The takeaway: parsing the output into a schema before it touches storage is what stops malformed rows, while handing the agent the write tool directly gives it more autonomy and more ways to go wrong. That result is what drives the design of the task manager above.

LLM & RAG

Self-Syncing RAG Knowledge Base

RAGPineconeEmbeddingsGoogle Driven8n
Working +
Problem

A RAG system that needs a human to re-run ingestion goes stale the moment someone drops a new file in the folder. Naively re-indexing everything on a schedule is the usual fix, and it wastes embedding calls and duplicates chunks.

Solution

A knowledge base that keeps itself current: it watches a Google Drive folder, ingests only documents it hasn't seen before, and serves a chat agent that answers strictly from what has been indexed.

Implementation

A scheduled trigger lists the Drive folder and cross-references it against a Google Sheets ledger of already-processed files; a code node computes the difference, and only new files go through the loop that downloads, splits, and embeds them. Documents are chunked with a recursive character splitter, embedded via HuggingFace Inference, and stored in Pinecone. On the query side, the vector store is exposed to the agent as a retrieval tool rather than being stuffed into the prompt, so the model decides when a lookup is warranted. Models run through OpenRouter with Groq as a fallback.

The Softmax Problem: Rejecting Unknown Classes

Bayesian Neural NetworksMulti-LabelUncertainty
Research +
GitHub — full write-up & notebook ↗
Problem

A standard multi-class classifier always predicts something. Softmax forces the probabilities to sum to one, so an input belonging to none of the trained classes still gets confidently assigned to the nearest one.

Solution

Two ways out, worked through in the repository: Bayesian neural networks, which carry uncertainty in the prediction itself, and reframing the task as multi-label with sigmoid outputs — where each class is scored independently and every score can fall below threshold, letting the model reject the input entirely.

Implementation

Written up with a notebook implementing the multi-label approach. The repository explains the reasoning in full — it's a write-up rather than a demo, so it's linked rather than screenshotted.

Production WhatsApp Messaging Platform

WhatsApp Cloud APIMongoDBWebhook SecuritySelf-hosted n8nHostinger VPS
Production +

Client work. Described at the level of the engineering only — no diagrams, workflow files, or client identifiers.

Problem

Running outbound WhatsApp messaging at scale on the official API means living with its constraints: template approval, per-number rate limits, delivery webhooks that arrive out of order, and media identifiers that expire after 30 days and silently break every message referencing them.

Solution

A set of automation workflows sitting between a web application and the WhatsApp Business Cloud API, handling outbound sends, inbound replies, scheduled reminders, and the maintenance jobs that keep the whole thing from decaying — with MongoDB as the single source of truth for what has been sent, delivered, and answered.

Implementation

Sends go to the Graph API as approved template messages; inbound replies arrive on webhooks and are matched back to records in MongoDB. Every webhook is authenticated — a shared secret header between the application and the automation layer, and HMAC signature verification on the callbacks coming from Meta, so an endpoint that is public by necessity still can't be driven by anyone else.

Large sends are chunked and paced with batching and deliberate waits rather than fired in one burst, which is what keeps them inside the API's rate limits. Scheduled jobs handle the time-based side: reminders for non-responders, follow-ups, and expiry. The 30-day media limit is handled by a job that re-uploads assets and rewrites the stored identifiers before they lapse, alongside a cleanup job that removes orphaned files so disk on the VPS doesn't grow without bound.

Also covered

Self-hosting and operating n8n on a Hostinger VPS — deployment, environment and credential management, HTTPS, persistence, and keeping long-running scheduled workflows alive.

Fire & Smoke Detection from IoT Sensors

Scikit-learnNeural NetworkEnsembleStreamlit
Live demo +
Try it live ↗ GitHub ↗
Problem

Detecting fire from environmental sensors early enough to matter. A single classifier gives you a yes or no with no sense of how much to trust it — and for a safety signal, that's the part you care about.

Solution

A web app that takes thirteen live sensor readings — temperature, humidity, TVOC, eCO2, raw hydrogen and ethanol, pressure, and particulate counts — and shows the verdict from seven different models at once. Agreement across all seven is a far stronger signal than any one of them alone.

Implementation

Trained on the IoT smoke-detection dataset: logistic regression, decision tree, random forest, naive Bayes, histogram gradient boosting, a voting ensemble, and a Keras neural network. Every model is trained, serialized, and loaded by the app, which runs all of them on each input and reports them side by side rather than hiding the disagreement behind one number. Deployed on Streamlit.
